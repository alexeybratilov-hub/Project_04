### А.3. Ключевые зависимости и архитектурные ограничения
- **Мульти-юрлицо (`DatabaseState.entities[]`)**: в `App.tsx` `dbState.tabs` зеркалирует только таблицы **активного** юрлица, а остальные юрлица лежат в `dbState.entities`. - **Лимит 20 вкладок в `TabBar.tsx` и `App.tsx`**: `TabBar` ограничивает создание вкладок (`tabs.length < 20`). Системная вкладка `«Контроль сроков»` не должна занимать пользовательский слот в `entity.tabs`, попадать в `TemplatesModal`/`RelationsSchemaModal`/`ExcelImportModal` или ломать `tabs.length <= 1` защиту. Оптимально реализовать её как **виртуальную закреплённую системную вкладку** в `TabBar` + производную агрегацию без дублирования данных.
- **Совместимость с `T-37`–`T-44`**: нельзя нарушать `sticky left/right` колонки, перенос заголовков (`MIN_COLUMN_WIDTH = 88`), Drag-and-Drop переупорядочивание столбцов (`reorderUtils.ts`) и вкладок (`TabBar.tsx`), Excel-выделение (`dataGridSelection.ts`) и локальные ревизии сохранения (`storageService.ts`).

## Б. Модель хранения данных

### Б.1. Расширение типов (`src/types/database.ts`)
1. **`ColumnType`**:
   ```ts
   export type ColumnType =
     | 'text'
     | 'number'
     | 'date'
     | 'select'
     | 'boolean'
     | 'link'
     | 'relation'
     | 'deadline_control';
   ```
   В `COLUMN_TYPE_LABELS` добавляется: `deadline_control: 'Контроль сроков'`.

2. **Конфигурация столбца (`DeadlineColumnConfig` в `Column.deadlineConfig`)**:
   ```ts
   export type DeadlinePeriodicityUnit = 'days' | 'months' | 'years';
   export type DeadlineWarningDayType = 'calendar' | 'working';

   export interface DeadlineColumnConfig {
     periodicityValue: number;            // >= 0 (0 = разовый срок без автосдвига)
     periodicityUnit: DeadlinePeriodicityUnit;
     warningValue: number;                // >= 0 (порог статуса «скоро»)
     warningDayType: DeadlineWarningDayType;
   }
   ```
   По умолчанию при создании столбца: `{ periodicityValue: 12, periodicityUnit: 'months', warningValue: 14, warningDayType: 'calendar' }`.

3. **Значение ячейки (`DeadlineCellValue` в `row[col.id]`)**:
   ```ts
   export interface DeadlineCellValue {
     actualDate?: string;       // ISO YYYY-MM-DD (фактическая дата проведения)
     manualNextDate?: string;   // ISO YYYY-MM-DD (явная ручная следующая дата)
     completed?: boolean;       // явная отметка «Выполнено» (актуально для разовых сроков без периодичности или закрытых вручную)
     completedAt?: string;      // ISO YYYY-MM-DD (дата фиксации выполнения)
     note?: string;             // краткий комментарий (опционально)
     _rawOriginal?: string;     // сохранённый исходный текст при конверсии нераспознанных значений
   }
   ```
   *Обоснование выбора `row[col.id]` вместо набора скрытых колонок*: хранение в одном объекте внутри `row[col.id]` гарантирует автоматическую сохранность при переупорядочивании столбцов (`T-42`), переименовании (`T-40`), переносе строк, копировании/удалении и проверках связей по `column.id`. Никаких «расползающихся» служебных столбцов в таблице не возникает.

4. **Настройки приложения (`AppSettings.deadlineSettings`)**:
   ```ts
   export interface DeadlineAppSettings {
     holidays?: string[];              // пользовательский список нерабочих/праздничных дат YYYY-MM-DD
     snoozedNotificationKeys?: Record<string, string>; // ключ события -> YYYY-MM-DD (скрыто до смены дня/даты)
     notificationsEnabled?: boolean;   // default true
   }
   ```

### Б.2. Привязка данных и отсутствие дублирования
- **Источник правды**: первичные данные хранятся **только** в `entities[i].tabs[j].rows[k][col.id]` (и конфигурации `columns[m].deadlineConfig`).
- **Сводная вкладка «Контроль сроков»** не создаёт отдельной копии строк в JSON БД — список событий вычисляется реактивно (мемоизированный селектор `collectDeadlineEvents(dbState)`), пробегая по всем `entities` → `tabs` → столбцам с `type === 'deadline_control'` → `rows`.
- Это исключает рассинхронизацию при редактировании ячеек, удалении сотрудников, клонировании юрлица и импорте из Excel.

### Б.3. Совместимость с JSON и резервными копиями
- В `DatabaseState` версия `'1.3.0'` (или минорный bump `'1.3.1'` при `major = 1`, который `inspectDatabaseBackupText` принимает без блокировки). Рекомендуется оставить `'1.3.0'` либо `'1.3.1'` с полностью опциональными полями `deadlineConfig` и `deadlineSettings`, чтобы старые бэкапы открывались без миграционных сбоев, а новые бэкапы корректно валидировались:
  - `validateTabStructure` не отклоняет `type === 'deadline_control'` и объектные значения в `row[col.id]`.
  - `normalizeDatabaseState` нормализует `deadlineConfig` на колонках `deadline_control` и `settings.deadlineSettings`, а также корректно обрабатывает случаи, когда в `row[col.id]` такого столбца оказалась строка (например, после ручного редактирования JSON или вставки даты строкой) — через безопасный парсер `normalizeDeadlineCellValue(raw)`.

## В. Правила расчёта и статусы

### В.1. Календарная арифметика (без смещения часовых поясов)
- Все даты хранятся и вычисляются строго как календарные даты `YYYY-MM-DD` (без преобразований через UTC/часовой пояс браузера, чтобы избежать сдвига на `-1 день` в регионах РФ).
- Входной парсер поддерживает форматы `YYYY-MM-DD`, `ДД.ММ.ГГГГ`, `ДД/ММ/ГГГГ` (а также числовые даты Excel при импорте). Невалидные даты (например `31.02.2026`) отклоняются парсером.

### В.2. Расчёт плановой следующей даты (`calculatedNextDate` и `effectiveNextDate`)
1. Если указана `actualDate` и `periodicityValue > 0`:
   - `days`: прибавить `periodicityValue` календарных дней.
   - `months`: прибавить `periodicityValue` месяцев с безопасным зажимом конца месяца (например, `2026-01-31` + 1 мес → `2026-02-28`, `2024-02-29` + 12 мес → `2025-02-28`).
   - `years`: прибавить `periodicityValue` лет с зажимом `29.02` → `28.02` для невисокосного года.
2. Если `periodicityValue === 0` (разовый контроль без цикла): `calculatedNextDate = undefined`.
3. **Приоритет ручной плановой даты**:
   - Если задана `manualNextDate`: `effectiveNextDate = manualNextDate`, источник даты — `'manual'` (в интерфейсе отмечается как «задана вручную», при этом расчётная дата остаётся видимой в карточке ячейки для справки).
   - Иначе `effectiveNextDate = calculatedNextDate`, источник — `'auto'`.

### В.3. Пересчёт при вводе новой фактической даты
- При вводе новой `actualDate` (в ячейке таблицы или через кнопку «Отметить выполнение» в «Контроле сроков»):
  - `actualDate` обновляется на введённую дату;
  - флаг `completed` для разового срока без периодичности переводится в `true` (если цикл `periodicityValue > 0`, то `completed` не блокирует новый цикл, а сбрасывается для нового периода);
  - **правило для `manualNextDate`**: при изменении `actualDate` устаревшая ручная плановая дата `manualNextDate` **очищается** (чтобы система пересчитала новый плановый срок от новой фактической даты). Исключение — если пользователь в этом же редактировании явно задал новую `manualNextDate`. В окне редактирования ячейки пользователь явно видит, что ручная дата сбросится и применится авторасчёт, либо может тут же указать новую ручную дату.

### В.4. Рабочие и календарные дни до срока (`daysRemaining`)
- Пусть `today` — локальная календарная дата (`YYYY-MM-DD`).
- **Календарные дни** (`warningDayType === 'calendar'`):
  - `calendarDiff = effectiveNextDate - today` (в днях; `< 0` при просрочке, `0` если сегодня).
- **Рабочие дни** (`warningDayType === 'working'`):
  - Подсчёт дней на полуинтервале `(today, effectiveNextDate]` (при `effectiveNextDate >= today`), исключая субботу, воскресенье и даты из `settings.deadlineSettings.holidays`.
  - Если `effectiveNextDate < today`, возвращается отрицательное количество рабочих дней просрочки (на интервале `(effectiveNextDate, today]`).
- Порог «скоро» сравнивается с `remainingByType <= warningValue`, где тип дней соответствует `column.deadlineConfig.warningDayType`.

### В.5. Определение статусов (детерминированная таблица приоритетов)
Статусы вычисляются чистой функцией `evaluateDeadlineStatus(cell, config, today, holidays)`:
1. **`выполнено` (`completed`)**:
   - Наступает, если для разового мероприятия (`periodicityValue === 0` или когда следующая плановая дата не назначена) проставлено `completed === true` (или заполнена `actualDate` без плановой следующей даты и не задана более ранняя невыполненная `manualNextDate`).
   - *Примечание для периодических мероприятий*: при отметке «Выполнено» по периодическому столбцу (`periodicityValue > 0`) сразу фиксируется новая `actualDate`, вычисляется новый `effectiveNextDate` в будущем и запись переходит в актуальный плановый цикл (`запланировано` или `скоро` при коротком периоде). Дополнительно сохраняется `completedAt`, чтобы в истории/подсказке было видно дату последнего закрытия.
2. **`данные отсутствуют` (`missing_data`)**:
   - Не удалось получить `effectiveNextDate` (нет ни `actualDate`, ни `manualNextDate`), и не выполняется условие `выполнено`. Если есть `_rawOriginal`, UI помечает это отдельной подсказкой («Исходный текст не распознан как дата»).
3. **`просрочено` (`overdue`)**:
   - `effectiveNextDate < today` (разница дней `< 0`).
4. **`скоро` (`due_soon`)**:
   - `effectiveNextDate >= today` и `remainingByConfiguredType <= config.warningValue`.
5. **`запланировано` (`scheduled`)**:
   - `effectiveNextDate >= today` и `remainingByConfiguredType > config.warningValue`.

### В.6. Изменение параметров периодичности
- При изменении `periodicityValue`, `periodicityUnit` или `warningValue`/`warningDayType` в настройках столбца существующие `actualDate` и `manualNextDate` в строках **не изменяются и не удаляются**.
- Все `calculatedNextDate` и статусы пересчитываются автоматически; для ручных `manualNextDate` пересчитывается только статус (`скоро`/`запланировано`/`просрочено`) по новому порогу предупреждения.

### В.7. Дедупликация уведомлений
- Уникальный идентификатор уведомления:  
  `notificationKey = ${entityId}::${tabId}::${rowId}::${colId}::${effectiveNextDate}::${status}`
- Повторные перерисовки React, переключения вкладок, редактирование других строк и переключение юрлиц не вызывают повторных всплывающих уведомлений:
  - В текущей сессии используется `shownToastKeysRef: Set<string>`.
  - При «Отложить / Ознакомлен» в интерфейсе ключ записывается в `settings.deadlineSettings.snoozedNotificationKeys[notificationKey] = today` (сбрасывается автоматически, если изменится `effectiveNextDate` или статус перейдёт из `due_soon` в `overdue`).

## Г. Структура интерфейса (UI)

Придерживаемся сдержанной рабочей desktop-эстетики (Apple-подобная чистота, чёткая иерархия, компактная плотность под `1366×768`, `1920×1080` и масштабирование `125%/150%`, без лишней декоративности и карточного шума).

### Г.1. Создание и настройка столбца `'deadline_control'`
1. **`ColumnEditorModal.tsx`**:
   - В выборе типа нового столбца добавляется вариант `Контроль сроков`.
   - При выборе (или редактировании) столбца `'deadline_control'` раскрывается компактная группа настроек параметров цикла: периодичность (число + `дн. / мес. / лет`), порог предупреждения (число + `календарных / рабочих дн.`).
   - Для существующих столбцов `deadline_control` добавляется кнопка настройки параметров периодичности и **кнопка «Изменить тип...»**.
2. **`DataGrid.tsx` (быстрое добавление `+`) и `NewTabModal.tsx`**:
   - В выпадающем списке типов добавляется `Контроль сроков` (при быстром создании применяются дефолтные параметры `12 мес. / 14 кал. дн.` с возможностью тут же открыть расширенный редактор).

### Г.2. Отображение и редактирование ячейки в `DataGrid`
- **Состояние просмотра**: компактный двухстрочный блок внутри ячейки без выхода за ширину колонки:
  - Верхняя строка: плановая дата (крупно, моноширинно `tabular-nums`, при ручной дате — мини-метка `ручн.`) + компактный статусный бейдж (`Просрочено`, `Скоро · N дн.`, `Запланировано`, `Выполнено`, `Нет даты`).
  - Нижняя строка (приглушённая): `Факт: ДД.ММ.ГГГГ` (если есть) и при наличии `_rawOriginal` — значок предупреждения о нераспознанном исходнике.
- **Состояние выделения (`T-41`)**: одиночный клик выделяет ячейку, `Ctrl+C` копирует читаемое представление (`План: ДД.ММ.ГГГГ (Статус) | Факт: ДД.ММ.ГГГГ` или эффективную дату в TSV).
- **Редактирование (двойной клик / `F2` / `Enter`)**:
  - Аккуратный popover-редактор рядом с ячейкой (`Z_INDEX.popover`, закрытие по `Esc` без сохранения или `Сохранить` / `Enter`):
    - Поле «Фактическая дата» (`<input type="date">`) + быстрая кнопка «Сегодня».
    - Поле «Плановая следующая дата» (`<input type="date">`, пусто = авторасчёт по периодичности; при наличии значения показывается кнопка «Сбросить на авторасчёт»).
    - Предпросмотр итоговой даты и статуса в реальном времени (с указанием источника: авто или вручную).
    - Чекбокс/действие «Отметить как выполнено» (для разовых сроков или фиксации выполнения).
    - Краткое примечание (опционально) и отображение `_rawOriginal`, если значение было сконвертировано с предупреждением.

### Г.3. Безопасная смена типа существующего столбца
- В `ColumnEditorModal.tsx` у каждого столбца появляется действие «Изменить тип».
- При выборе нового типа открывается вложенный диалог/секция конвертации (`layer="nested"`):
  - Для перехода **`text`/`date` → `deadline_control`**:
    - Выбор роли существующих значений в ячейках: «Использовать как фактическую дату (рекомендуется — рассчитает следующий срок)» или «Использовать как ручную плановую дату».
    - **Обязательное превью перед подтверждением**: статистика по всем строкам таблицы — сколько дат распознано (`YYYY-MM-DD`, `ДД.ММ.ГГГГ`), сколько пустых, сколько нераспознанных строк (пример до 5 значений). Нераспознанные строки **не удаляются**, а сохраняются в `_rawOriginal` с пометкой в ячейке.
  - Для перехода **`deadline_control` → `date` / `text`**:
    - Выбор, какое значение сохранить в ячейку (`effectiveNextDate` или `actualDate`, либо текстовую сводку `Факт / План` для `text`), + превью перед подтверждением.
  - Ограничения безопасности: блокировка смены типа для столбца с активной связью `relation` (с понятным объяснением сначала открепить связь); единый коммит в `ColumnEditorModal` через `Сохранить`.

### Г.4. Постоянная системная вкладка «Контроль сроков»
- **`TabBar.tsx`**:
  - Первая вкладка в полосе (закреплена перед перетаскиваемыми пользовательскими вкладками) — системная вкладка `«Контроль сроков»` с иконкой часов/календаря и суммарным счётчиком `просрочено + скоро` (при 0 — спокойный нейтральный вид).
  - Не поддерживает перетаскивание (`draggable={false}`), двойной клик для переименования и удаление (`onDeleteTab` заблокирован на уровне UI и `App.tsx`).
  - Контекстное меню для системной вкладки отключено или содержит только «Открыть» / «Обновить».
- **`DeadlineControlView.tsx`** (рабочая область при активной системной вкладке):
  - **Верхняя панель сводки и фильтров**:
    - 4 компактных фильтра-счётчика по статусам: `Все`, `Просрочено`, `Скоро`, `Запланировано`, `Выполнено / Нет данных`.
    - Выпадающие фильтры: **Юридическое лицо** (`Все юрлица` / конкретное юрлицо), **Таблица**, **Сотрудник / объект**, **Статус** + строка быстрого поиска.
    - Кнопка настройки нерабочих/праздничных дат (компактный модал/поповер для `holidays`).
  - **Таблица событий**:
    - Колонки с закреплёнными заголовками (`sticky top-0`): Юрлицо, Таблица, Сотрудник / запись, Столбец (мероприятие), Факт. дата, План. дата (с меткой `ручн.` при переопределении), Осталось / просрочка (в раб./кал. днях по настройке столбца), Статус, Действия (`Перейти к записи`, `Выполнено сегодня`).
    - Переход к записи переключает `activeEntityId` (если запись в другом юрлице), `activeTabId` и подсвечивает нужную строку (`highlightRowTemporarily`) с автопрокруткой на страницу.

### Г.5. Панель и индикатор уведомлений в верхней панели
- В `MenuBar.tsx` (слева от индикатора LLM-статуса, с адаптивной компактностью) размещается кнопка-индикатор сроков:
  - Отображает счётчик активных проблемных сроков (красный бейдж при наличии `просрочено`, янтарный при наличии только `скоро`, нейтральный серый/зелёный при отсутствии).

- При открытии/загрузке базы (если есть неподтверждённые `overdue`/`due_soon`) показывается одно дедуплицированное ненавязчивое toast-уведомление с переходом во вкладку контроля сроков.

## Е. Миграция и обратная совместимость

1. **Существующие таблицы и старые бэкапы**:
   - Старые базы (`version: '1.3.0'`, а также ранние `1.0`–`1.2`) не содержат колонок `'deadline_control'` и `settings.deadlineSettings`.
   - `storageService.normalizeDatabaseState()` при загрузке оставляет старые колонки без изменений и подставляет безопасные значения по умолчанию для `deadlineSettings` только в памяти (без принудительной перезаписи файла на диске до первого пользовательского изменения).
   - При импорте старого бэкапа в `BackupModal` (`inspectDatabaseBackupText`) проверка схемы пройдёт без ложных предупреждений.
2. **Преобразование существующих столбцов (`ColumnEditorModal`)**:
   - Перед применением смены типа выполняется прогон `previewColumnTypeConversion(rows, fromType, toType, options)`:
     - подсчёт успешных дат, пустых ячеек и нераспознанных значений;
     - нераспознанный текст (`"по графику"`, `"уточнить"`) **никогда не затирается молча**: сохраняется в `DeadlineCellValue._rawOriginal` (при переходе в `deadline_control`) или остаётся строкой (при переходе в `text`).
   - В окне `ColumnEditorModal` отображается табличка/сводка предпросмотра с числом затрагиваемых записей; без подтверждения пользователя конвертация не применяется.
3. **Аварийное восстановление и откат**:
   - Перед сохранением массовой конверсии типа столбца на диске срабатывает штатная защита ревизий и ротации бэкапов (`launcher.c`), а при входе в `ColumnEditorModal` черновик изолирован (кнопка «Отмена» откатывает всё до коммита).
   - Дополнительно перед выполнением необратимой конверсии с потерями полей (например, при выборе отбрасывания части полей в `deadline_control → date`) в `App.tsx` можно создавать снимок состояния через `storageService` (локальный снимок / бэкап аналогично предсбросовой защите).
4. **Совместимость с Excel и шаблонами документов**:
   - Вся логика сериализации (`excelService`, `dataGridSelection`, `documentGenerator`) обязана проверять `typeof val === 'object'` и `column.type === 'deadline_control'`, возвращая отформатированную дату (`ДД.ММ.ГГГГ` или `YYYY-MM-DD`) и никогда не выводя `[object Object]`.
