## Б. Модель хранения данных

### Б.1. Расширение типов (`src/types/database.ts`)
1. **`ColumnType`**:
   ```ts
   export type ColumnType =
     | 'text'
     | 'number'
     | 'date'
     | 'select'
     | 'boolean'
     | 'link'
     | 'relation'
     | 'deadline_control';
   ```
   В `COLUMN_TYPE_LABELS` добавляется: `deadline_control: 'Контроль сроков'`.

2. **Конфигурация столбца (`DeadlineColumnConfig` в `Column.deadlineConfig`)**:
   ```ts
   export type DeadlinePeriodicityUnit = 'days' | 'months' | 'years';
   export type DeadlineWarningDayType = 'calendar' | 'working';

   export interface DeadlineColumnConfig {
     periodicityValue: number;            // >= 0 (0 = разовый срок без автосдвига)
     periodicityUnit: DeadlinePeriodicityUnit;
     warningValue: number;                // >= 0 (порог статуса «скоро»)
     warningDayType: DeadlineWarningDayType;
   }
   ```
   По умолчанию при создании столбца: `{ periodicityValue: 12, periodicityUnit: 'months', warningValue: 14, warningDayType: 'calendar' }`.

3. **Значение ячейки (`DeadlineCellValue` в `row[col.id]`) — минимально необходимая модель**:
   ```ts
   export interface DeadlineCellValue {
     actualDate?: string;       // ISO YYYY-MM-DD — фактическая дата последнего выполнения
     manualNextDate?: string;   // ISO YYYY-MM-DD — явное ручное переопределение следующей плановой даты
     note?: string;             // краткий комментарий (опционально)
     _rawOriginal?: string;     // исходное строковое значение (при конверсии нераспознанного текста)
   }
   ```
   *Обоснование отказа от `completed` и `completedAt`*:
   - Поля `completed: boolean` и `completedAt: string` избыточны и создают конфликт источников правды. В предметной области ОТ факт внесения `actualDate` (вручную или кнопкой «Выполнено сегодня») **и есть** фиксация выполнения мероприятия на эту дату.
   - После внесения `actualDate`:
     - для периодического столбца (`periodicityValue > 0`) сразу вычисляется новый плановый срок следующего цикла;
     - для разового столбца (`periodicityValue === 0`) заполненная `actualDate` при отсутствии более поздней `manualNextDate` однозначно переводит событие в статус `выполнено`.
   - Хранение в одном объекте внутри `row[col.id]` (вместо набора служебных колонок) гарантирует автоматическую сохранность при переупорядочивании столбцов (`T-42`), переименовании (`T-40`), переносе строк, копировании/удалении и проверках связей по `column.id`.

4. **Настройки приложения (`AppSettings.deadlineSettings`)**:
   ```ts
   export interface DeadlineAppSettings {
     holidays?: string[];              // пользовательский список нерабочих/праздничных дат YYYY-MM-DD (отсортированный, без дублей)
     snoozedNotificationKeys?: Record<string, string>; // notificationKey -> hideUntil (YYYY-MM-DD; скрыто пока today < hideUntil)
     notificationsEnabled?: boolean;   // default true
   }
   ```

### Б.2. Привязка данных и отсутствие дублирования
- **Источник правды**: первичные данные хранятся **только** в `entities[i].tabs[j].rows[k][col.id]` (и конфигурации `columns[m].deadlineConfig`).
- **Сводная вкладка «Контроль сроков»** не создаёт отдельной копии строк в JSON БД — список событий вычисляется реактивно (мемоизированный селектор `collectDeadlineEvents(dbState)`), пробегая по всем `entities` → `tabs` → столбцам с `type === 'deadline_control'` → `rows`.
- Это исключает рассинхронизацию при редактировании ячеек, удалении сотрудников, клонировании юрлица и импорте из Excel.

### Б.3. Совместимость с JSON и резервными копиями
- В `DatabaseState` сохраняется версия `'1.3.0'` (или минорный bump `'1.3.1'` при `major = 1`, который `inspectDatabaseBackupText` принимает без блокировки) с опциональными полями `deadlineConfig` и `deadlineSettings`, чтобы старые бэкапы открывались без сбоев:
  - `validateTabStructure` не отклоняет `type === 'deadline_control'` и объектные значения в `row[col.id]`.
  - `normalizeDatabaseState` нормализует `deadlineConfig` на колонках `deadline_control`, сортирует/дедуплицирует `settings.deadlineSettings.holidays`, очищает просроченные записи `snoozedNotificationKeys` и безопасно приводит строковые значения ячеек к `DeadlineCellValue` через `normalizeDeadlineCellValue(raw)`.

## В. Правила расчёта и статусы

### В.1. Календарная арифметика (без смещения часовых поясов)
- Все даты хранятся и вычисляются строго как календарные даты `YYYY-MM-DD` (целочисленная календарная арифметика `(year, month, day)` без преобразований через UTC/часовой пояс браузера, что исключает сдвиг на `-1 день` в регионах РФ).
- Входной парсер поддерживает форматы `YYYY-MM-DD`, `ДД.ММ.ГГГГ`, `ДД/ММ/ГГГГ` (а также числовые даты Excel при импорте) с проверкой календарной корректности (даты вроде `31.02.2026` или `29.02.2025` отклоняются).

### В.2. Разделение периодичности и срока предупреждения; правила расчёта дат
В конфигурации столбца `DeadlineColumnConfig` строго разделены два независимых параметра:
1. **Периодичность мероприятия (`periodicityValue`, `periodicityUnit`)** — определяет **цикл повторения** и расчёт следующей плановой даты от `actualDate`.
   - Поддерживаемые единицы периодичности:
     - `'days'` — календарные дни (`periodicityValue >= 0`);
     - `'months'` — календарные месяцы (`periodicityValue >= 0`);
     - `'years'` — календарные годы (`periodicityValue >= 0`).
   - Особое значение `periodicityValue === 0`: **разовое мероприятие** без автоматического расчёта следующего срока (`calculatedNextDate = undefined`).
   - Пример: `periodicityValue = 12, periodicityUnit = 'months'` задаёт ежегодный цикл независимо от настроек предупреждения.
   - **Точные правила расчёта `calculatedNextDate` от `actualDate`**:
     - `days`: прибавляется `periodicityValue` календарных дней в григорианском календаре.
     - `months`: месяц увеличивается на `periodicityValue` с переносом целых лет; число дня ограничивается последним днём целевого месяца (`min(day, daysInMonth(targetYear, targetMonth))`). Примеры: `2026-01-31 + 1 мес. = 2026-02-28`; `2024-01-31 + 1 мес. = 2024-02-29`; `2026-03-31 + 3 мес. = 2026-06-30`.
     - `years`: год увеличивается на `periodicityValue`, месяц сохраняется, число дня ограничивается `daysInMonth(targetYear, month)` для обработки `29 февраля`. Примеры: `2024-02-29 + 1 год = 2025-02-28`; `2024-02-29 + 4 года = 2028-02-29`.
2. **Срок заблаговременного предупреждения (`warningValue`, `warningDayType`)** — влияет **только** на момент перехода предстоящего события из статуса `запланировано` в статус `скоро` и отображение уведомлений; **не сдвигает** `calculatedNextDate` и `effectiveNextDate`.
   - Например, при периодичности `12 месяцев` можно задать предупреждение за `30 рабочих дней` (`warningValue = 30, warningDayType = 'working'`).
3. **Приоритет ручной плановой даты (`manualNextDate`)**:
   - Если задана `manualNextDate`, то `effectiveNextDate = manualNextDate` (источник `'manual'`, в UI помечается как «вручную», при этом `calculatedNextDate` остаётся доступной для справки в карточке редактирования).
   - Иначе `effectiveNextDate = calculatedNextDate` (источник `'auto'`).

### В.3. Поведение при внесении новой фактической даты
При вводе новой `actualDate` (вручную в поповере или по нажатию «Выполнено сегодня»):
1. `actualDate` перезаписывается новой датой выполнения.
2. Предыдущая `manualNextDate` **всегда сбрасывается (`undefined`)**, если пользователь в том же действии явно не вводит новую ручную плановую дату. Это гарантирует пересчёт следующего срока от новой фактической даты по правилам периодичности без залипания старых ручных коррекций.
3. При необходимости пользователь может сразу или позже задать новую `manualNextDate` (переопределив новый расчётный срок).

### В.4. Алгоритм подсчёта календарных и рабочих дней и учёт пользовательских нерабочих дат
Пусть `today` — текущая локальная календарная дата (`YYYY-MM-DD`).

1. **Источники нерабочих дней**:
   - **Обязательное ограничение архитектуры**: приложение работает автономно (в том числе с USB через `OT-Baza.exe`) и **не предполагает наличия актуального производственного календаря РФ** без отдельного источника данных. Автоматические сетевые запросы и вшитый бессрочный «официальный» календарь не используются.
   - Нерабочими днями при расчёте `working` считаются:
     - **выходные дни**: суббота и воскресенье (`dayOfWeek === 0 || dayOfWeek === 6`);
     - **пользовательские нерабочие даты**: множество дат из `DatabaseState.settings.deadlineSettings.holidays` (`Set<string>` в формате `YYYY-MM-DD`).
2. **Хранение и редактирование пользовательских нерабочих дат**:
   - Массив `settings.deadlineSettings.holidays` хранится в `./data/ot_database.json` (совместно с настройками БД, сохраняется в резервных копиях).
   - Во вкладке «Контроль сроков» доступна компактная панель/модал «Нерабочие / праздничные дни»: добавление даты через `<input type="date">`, вставка перечня дат строкой (`ДД.ММ.ГГГГ` / `YYYY-MM-DD`), удаление и фильтрация по году.
   - Изменение списка `holidays` мгновенно пересчитывает `daysRemaining` и статус `скоро`/`запланировано` при чтении без модификации значений ячеек `row[col.id]`.
3. **Алгоритм вычисления `daysRemaining` между `today` и `effectiveNextDate`**:
   - **Календарные дни (`warningDayType === 'calendar'`)**:
     - Вычисляется точная знаковая разница календарных дней `calendarDaysDiff = diffDays(today, effectiveNextDate)` (`> 0` — осталось дней, `0` — срок сегодня, `< 0` — дней просрочки).
   - **Рабочие дни (`warningDayType === 'working'`)**:
     - Если `effectiveNextDate === today`: `workingDaysDiff = 0`.
     - Если `effectiveNextDate > today`: перебираются даты строго на полуинтервале `(today, effectiveNextDate]` и подсчитываются дни, не являющиеся выходными (Сб/Вс) и не входящие в `holidays`.
     - Если `effectiveNextDate < today`: перебираются даты на полуинтервале `(effectiveNextDate, today]`, возвращается отрицательное значение `-count` (количество рабочих дней просрочки).
     - *Защита граничного случая*: факт просрочки (`effectiveNextDate < today`) всегда проверяется **по календарному сравнению дат**, а не по `workingDaysDiff < 0` — поэтому событие, чей срок выпал на пятницу, уже в субботу имеет статус `просрочено` (даже если прошло `0` рабочих дней).

### В.5. Статусы и точные условия переходов
В модели чётко разделены две характеристики записи:
- **Статус последнего выполненного мероприятия (`lastExecution`)**:
  - `'performed'` — если заполнена `actualDate` (отображается как «Выполнено ДД.ММ.ГГГГ»);
  - `'none'` — если `actualDate` пуста («Не проводилось»).
- **Текущий статус контроля (`status`, строго взаимоисключающая машина состояний)**:
  1. **`выполнено` (`completed`)**:
     - **Единственное условие**: разовое мероприятие (`periodicityValue === 0`), у которого заполнена `actualDate` и **не задана** `manualNextDate` (`effectiveNextDate === undefined`).
     - *Почему нет противоречия с периодическими столбцами*: при `periodicityValue > 0` после внесения `actualDate` сразу появляется следующий расчётный срок цикла (`calculatedNextDate`). Запись немедленно переходит в статус **следующего** мероприятия (`запланировано`, `скоро` или `просрочено`), а факт прошедшего выполнения отображается через `lastExecution` (`Факт: ДД.ММ.ГГГГ`) в ячейке таблицы и в отдельной колонке «Факт. дата» системной вкладки.
  2. **`данные отсутствуют` (`missing_data`)**:
     - Не заполнена ни `actualDate`, ни `manualNextDate` (либо в результате конверсии сохранился только нераспознанный текст `_rawOriginal`).
  3. **`просрочено` (`overdue`)**:
     - Вычислена `effectiveNextDate` и по календарю `effectiveNextDate < today`.
  4. **`скоро` (`due_soon`)**:
     - Вычислена `effectiveNextDate`, по календарю `effectiveNextDate >= today`, и `daysRemainingByConfiguredType <= config.warningValue`.
  5. **`запланировано` (`scheduled`)**:
     - Вычислена `effectiveNextDate`, по календарю `effectiveNextDate >= today`, и `daysRemainingByConfiguredType > config.warningValue`.

**Таблица ключевых переходов**:
- `данные отсутствуют` → ввод `manualNextDate` → `запланировано` / `скоро` / `просрочено` (по соотношению с `today` и порогом).
- `данные отсутствуют` / `запланировано` / `скоро` / `просрочено` → ввод `actualDate` при `periodicityValue === 0` (сброс `manualNextDate`) → **`выполнено`**.
- `выполнено` (`periodicityValue === 0`) → установка новой `manualNextDate` → `запланировано` / `скоро` / `просрочено` (новый разовый контроль).
- `любой статус` → ввод `actualDate` при `periodicityValue > 0` (сброс `manualNextDate`) → расчёт новой `calculatedNextDate` → `запланировано` / `скоро` / `просрочено` нового цикла (с обновлением `lastExecution = actualDate`).
- Течение времени (`today` увеличивается) → `запланировано` → `скоро` (при входе в порог `warningValue`) → `просрочено` (на следующий день после `effectiveNextDate`).
- Очистка `actualDate` и `manualNextDate` → `данные отсутствуют`.

### В.6. Изменение параметров периодичности
- При изменении `periodicityValue`, `periodicityUnit` или `warningValue`/`warningDayType` в настройках столбца существующие `actualDate` и `manualNextDate` в строках **не изменяются и не удаляются**.
- Все `calculatedNextDate` и статусы пересчитываются динамически при чтении; для ручных `manualNextDate` пересчитывается только порог (`скоро`/`запланировано`/`просрочено`).

### В.7. Уведомления: дедупликация, повторы и откладывание
- В уведомления попадают события со статусом `overdue` или `due_soon`.
- Уникальный ключ уведомления:  
  `notificationKey = ${entityId}::${tabId}::${rowId}::${colId}::${effectiveNextDate}::${status}`
- **Дедупликация в рамках сессии**: множество `shownToastKeysRef: Set<string>` гарантирует, что переключение вкладок/юрлиц, фильтрация и перерисовки не порождают повторных всплывающих уведомлений для уже показанного `notificationKey`.
- **Условия повторного уведомления**:
  1. Эскалация статуса (`due_soon` → `overdue`) — формируется новый `notificationKey`, уведомление показывается повторно даже если предыдущее предупреждение откладывалось.
  2. Смена плановой даты (`effectiveNextDate` изменилась после переноса или нового цикла) — новый `notificationKey`.
  3. Новый запуск приложения (новая сессия), если срок остаётся в `due_soon`/`overdue` и не действует отложение (`snooze`).
- **Отложенные уведомления (`snoozedNotificationKeys`)**:
  - Действие «Скрыть на сегодня» сохраняет `snoozedNotificationKeys[notificationKey] = addDays(today, 1)` (`hideUntil`). Пока `today < hideUntil`, уведомление не всплывает при запуске/обновлении и скрыто из списка активных тостов (но сам объект события всегда остаётся видимым во вкладке «Контроль сроков»).
  - На следующий календарный день (`today >= hideUntil`), если проблема не устранена, уведомление снова становится активным; устаревшие ключи очищаются при нормализации БД.

## Е. Миграция, безопасность преобразования и обратная совместимость

1. **Совместимость со старыми таблицами и резервными копиями**:
   - Старые базы (`version: '1.3.0'`, а также ранние `1.0`–`1.2`) не содержат колонок `'deadline_control'` и `settings.deadlineSettings`.
   - `storageService.normalizeDatabaseState()` при загрузке оставляет старые колонки без изменений, нормализует `deadlineSettings` в памяти и не инициирует автоматическую перезапись файла на диске до первого пользовательского изменения.
   - В `BackupModal` (`inspectDatabaseBackupText`) старые и новые бэкапы с полями `DeadlineCellValue` (`actualDate`, `manualNextDate`, `note`, `_rawOriginal`) и `holidays` проходят валидацию без ошибок.
2. **Где хранится исходное значение при преобразовании**:
   - При конвертации обычного столбца (`text`, `date`, `number`, `select`, `boolean`, `link`) в `deadline_control` пользователь выбирает роль распознанных дат (`actualDate` или `manualNextDate`), а любые нераспознанные непустые значения сохраняются **без потери текста** в `DeadlineCellValue._rawOriginal`.
   - Таким образом, исходный текст не удаляется и остаётся доступен для просмотра в ячейке, в поповере редактирования и для обратного преобразования.
3. **Обратное преобразование (`deadline_control` → `text` / `date` / другие типы)**:
   - Выполняется также через обязательный шаг предпросмотра и подтверждения в `ColumnEditorModal`.
   - При переходе в `date`: пользователь выбирает источник — «Плановая дата (`effectiveNextDate`)» или «Фактическая дата (`actualDate`)»; превью заранее показывает число строк, где выбранная дата отсутствует (включая строки с одним `_rawOriginal`).
   - При переходе в `text`: пользователь выбирает формат — «Сводка `План / Факт`», «Только плановая дата», «Только фактическая дата» или «Восстановить исходное `_rawOriginal` (если сохранено)».
   - При переходе в несовместимые типы (`number`, `boolean`, `select`, `link`): превью явно предупреждает о строках, которые не преобразуются в целевой тип и потребуют ручного заполнения или останутся пустыми.
4. **Что происходит при удалении столбца `'deadline_control'`**:
   - Срабатывает штатный механизм `integrityService.getColumnDeleteImpact` + `InlineConfirm`: пользователь получает предупреждение о зависимых тегах шаблонов (`Tag`) и потере данных столбца.
   - После подтверждения столбец и значения `row[col.id]` удаляются из вкладки, связанные теги очищаются, а производные события этого столбца автоматически исчезают из вкладки «Контроль сроков» и счётчика уведомлений `MenuBar`.
   - Пользовательский список `settings.deadlineSettings.holidays` при удалении отдельного столбца не затрагивается; устаревшие `snoozedNotificationKeys` для удалённого `colId` игнорируются и подчищаются при нормализации.
5. **Резервные копии перед конверсией и поведение при неудачной миграции / сбое**:
   - До подтверждения в основном окне `ColumnEditorModal` все изменения находятся в изолированном черновике (кнопка «Отмена» или закрытие с подтверждением возвращает прежние столбцы и строки без следов).
   - Перед сохранением на диск подтверждённой смены типа столбца (если затронуты непустые ячейки) автоматически создаётся точка отката: в `native-fs` через `localApiClient.createBackup()`, в `web-preview` через `PRE_RESTORE_BACKUP_KEY` (`localStorage`), а содержимое всех `DeadlineCellValue` полностью включается в регулярные JSON-бэкапы.
   - Сама функция конверсии (`applyColumnTypeConversion`) чистая и атомарная над копией данных: при ошибке расчёта, отклонении пользователем или сбое записи на диск (ошибка ввода-вывода, конфликт ревизии, отключение USB по `T-37`) исходное состояние и предыдущая дисковая ревизия не повреждаются, пользователь видит статус ошибки и может повторить сохранение либо восстановиться из созданного бэкапа в `BackupModal`.
6. **Совместимость с Excel и шаблонами документов**:
   - `excelService`, `dataGridSelection` и `documentGenerator` используют единый форматтер `formatDeadlineCellDisplay`, исключая `[object Object]` в TSV, `.xlsx` и `{Тегах}` DOCX/PDF.

## Замечания, учтённые перед согласованием

При доработке технического плана учтены следующие уточнения:
1. **Упрощена модель фактического выполнения (п. 2.1)**: удалены избыточные поля `completed` и `completedAt` из `DeadlineCellValue`; единственным фактом выполнения является `actualDate`, внесение которой для периодических мероприятий автоматически пересчитывает следующий срок и сбрасывает устаревшую `manualNextDate`.
2. **Жёстко разделены периодичность и заблаговременное предупреждение (п. 2.2)**: явно закреплены поддерживаемые единицы (`days`, `months`, `years`, `0` для разовых), правила календарной арифметики конца месяца и `29 февраля`, а также независимость расчётной даты от `warningValue`.
3. **Уточнён алгоритм рабочих и календарных дней (п. 2.3)**: снято предположение о встроенном официальном производственном календаре РФ; зафиксированы правила учёта выходных (Сб/Вс) и пользовательских нерабочих дат `settings.deadlineSettings.holidays`, интерфейс их редактирования, способ хранения и защита граничного условия `просрочено` по календарной дате.
4. **Формализованы переходы статусов и правила уведомлений (п. 2.4)**: статус последнего выполненного мероприятия (`actualDate`) отделён от текущего статуса следующего срока (`выполнено` только для закрытых разовых событий без нового срока, для периодических — `запланировано`/`скоро`/`просрочено`); уточнены условия повторных уведомлений при эскалации/новой дате/новой сессии и механизм `snooze` («Скрыть на сегодня»).
5. **Детализирована безопасность конверсии типов (п. 3)**: зафиксированы хранение нераспознанных значений в `_rawOriginal`, сценарии обратного преобразования, последствия удаления столбца, автоматический предконверсионный бэкап, обязательный предпросмотр с подтверждением и поведение при сбое записи.
